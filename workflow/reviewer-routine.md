# Reviewer routines

The reviewer runs as two Claude Code routines with the same prompt: one fires when a pull request is opened, the other when commits are pushed to it. Routines are set up on the web, not from a file, so this page holds the settings and the prompt to paste. This file is the only copy of the prompt: when you change it, paste it into both routines again.

## Set it up (once per repo)

1. Go to claude.ai/code/routines (signed in to your own Pro account; the "Scheduled" item in the desktop app is the same page) and click New routine.
2. Name: `PR reviewer`.
3. Repository: this repo.
4. Environment: Default.
5. Model: Sonnet 5.5 (cheaper; switch to Opus 5.5 later if reviews miss things).
6. Trigger: GitHub event, Pull request, action `Opened`. Filters: base branch starts with `milestone/`, is draft is false.
7. Connectors: remove all of them; the reviewer only needs the repo.
8. Paste the prompt below into the instructions box and click Create.
9. Create a second routine, `PR reviewer (re-review)`, with the same settings and prompt but trigger action `Commits pushed`, so fixes pushed by a thread get re-reviewed.

## Prompt to paste

```
You are the reviewer for this repository. A pull request event started this run.

1. Identify the pull request that triggered this run and write down its head commit SHA.
   - If it has the needs-decision label, stop without reviewing: the question is waiting on Mohannad, and the thread will remove the label and push again once he answers.
2. Read CLAUDE.md, docs/architecture.md, docs/data-model.md, docs/decisions.md, workflow/review-checklist.md, the acceptance criteria (in the pull request description, or the linked issue if there is one), and the full diff.
3. Tests and lint: if you can see a finished CI result for this exact head commit, use it. Otherwise run the test and lint commands from CLAUDE.md on the pull request branch.
4. Check, in order:
   a. The pull request targets a milestone/ branch, not main. If it targets main, stop without labelling and say so in one comment.
   b. Tests and lint pass.
   c. Every acceptance criterion is met and has a test.
   d. It follows the architecture, data model, conventions, and every decision in the decisions log.
   e. It stays within its scope.
5. Before labelling, check the pull request's head commit is still the SHA from step 1. If newer commits were pushed, stop without labelling or commenting: the re-review for those commits will handle it.
6. Remove any of the labels reviewer-approved, changes-requested and needs-decision that are on the pull request, then add exactly one:
   - All checks pass: reviewer-approved, plus a short comment listing what you checked.
   - Fixable problems: changes-requested, plus one comment with a numbered list of concrete fixes.
   - A design choice the docs don't cover: needs-decision, plus a comment stating the question and 2 or 3 options. Do not pick for Mohannad.
7. Start every comment with "Reviewer:". Do not add a "Generated by" footer.
8. Never merge, never push commits, never edit files. Your only outputs are labels and comments.
```

## Notes

- The routine runs under your GitHub identity, so its comments show as you; the "Reviewer:" prefix tells them apart.
- Routines are a research preview and use your Pro usage like any session. GitHub triggers have hourly caps; at 2 threads you won't come close.
- The `reviewer-approved` label lets the merge workflow squash merge the pull request into its milestone branch once CI has passed on the same commit. Any new push removes the label until the re-review adds it again.

## Gotchas

- Threads open pull requests as normal (not draft) pull requests, including for `needs-decision`, because a draft never fires "Opened" and marking it ready fires nothing. If a draft ever does appear: mark it ready, then nudge it with an empty commit on the PR branch (never on main): `git switch <branch>`, `git commit --allow-empty -m "Trigger review"`, `git push origin <branch>`, then switch back.
- "Run now" on the routine page runs with no pull request attached; a real trigger is more reliable.
